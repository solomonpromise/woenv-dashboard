# Deploying WOEnv Dashboard

Three pieces, all on free tiers:

| Piece | Host | Notes |
| --- | --- | --- |
| Frontend (static SPA) | Vercel | No sleep, no expiry |
| Backend (FastAPI) | Render, free web service | 512 MB RAM, sleeps after 15 min idle |
| PostgreSQL | Neon, free project | 0.5 GB, no expiry |

Redis and Celery are not deployed. Nothing in the application ever enqueued a
task — workbook ingestion runs synchronously inside the upload request — so the
worker was idle and the broker existed only for it.

## 1. Push to GitHub

Both hosts deploy from a repository. From the project root:

```bash
git init && git add -A && git commit -m "Initial commit"
```

`.gitignore` already excludes `.env`, `venv/`, `node_modules/`, `dist/` and the
uploaded workbooks, which carry commercially sensitive well data. Confirm with
`git status` before pushing that no `.xlsx` files are staged.

## 2. Database — Neon

Create a project at [neon.tech](https://neon.tech), pick the region closest to
the Render region you will use below (Oregon → `us-west-2`), and copy the
connection string. It looks like:

```
postgresql://user:password@ep-xxxx.us-west-2.aws.neon.tech/neondb?sslmode=require
```

Use the **direct** endpoint, not the `-pooler` one: the API is a long-running
process with SQLAlchemy's own pool and `pool_pre_ping=True` already set, so it
handles Neon's auto-suspend without a external pooler.

If a provider ever hands you a `postgres://` URL, change the scheme to
`postgresql://` — SQLAlchemy 2 rejects the short form.

Do not use Render's own free PostgreSQL. It is deleted after 30 days.

## 3. Backend — Render

New → Blueprint, point it at the repository. It reads [`render.yaml`](render.yaml)
and prompts for the values marked `sync: false`:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | The Neon string from step 2 |
| `BACKEND_CORS_ORIGINS` | `["https://your-app.vercel.app"]` — a JSON array, see below |
| `ADMIN_PASSWORD` | A password you choose, for the first admin user |

`SECRET_KEY` is generated by Render and persists across deploys.

You will not know the Vercel URL yet. Put a placeholder in
`BACKEND_CORS_ORIGINS`, finish step 4, then come back and set it properly.

**`BACKEND_CORS_ORIGINS` must be a JSON array.** `pydantic-settings` parses it
as `List[str]`, so a bare `https://your-app.vercel.app` fails at boot with a
parse error rather than a helpful message. Include the scheme and no trailing
slash.

On first boot the entrypoint runs `scripts.migrate_schema` (creates the tables)
and then `scripts.seed_admin` because `ADMIN_PASSWORD` is set. **Delete the
`ADMIN_PASSWORD` variable once you have logged in** — leaving a password in the
environment is worth avoiding, and seeding is a no-op afterwards anyway.

Verify at `https://woenv-api.onrender.com/health`.

## 4. Frontend — Vercel

Import the repository, then:

| Setting | Value |
| --- | --- |
| Root Directory | `frontend` |
| Framework Preset | Vite (auto-detected) |
| Environment Variable | `VITE_API_URL` = `https://woenv-api.onrender.com` |

Everything else comes from [`frontend/vercel.json`](frontend/vercel.json).

**`VITE_API_URL` is read at build time,** not at runtime — Vite inlines it into
the bundle. Changing it requires a redeploy, not just a restart.

Give it the **origin only**. The `/api/v1` prefix is appended by the API client
in `src/services/api.ts`; including it here produces `/api/v1/api/v1/...` and
404s every request.

Then go back to Render and set `BACKEND_CORS_ORIGINS` to the real Vercel URL.

## Known limitations of this setup

**Cold starts.** The Render free instance sleeps after 15 minutes of inactivity.
The first request afterwards takes roughly 50 seconds, so the login screen will
appear to hang. If that matters, Koyeb's free tier does not sleep and takes the
same Docker image.

**Preview deployments fail CORS.** Every Vercel preview gets a unique URL, which
will not be in `BACKEND_CORS_ORIGINS`. Only the production domain works against
the deployed API. Fixing it properly means adding `allow_origin_regex` to the
CORS middleware in `app/main.py`.

**Uploads do not survive a restart.** The free plan has no persistent disk, so
`/app/uploads` is wiped whenever the instance sleeps or redeploys. Parsed data
is safe in Postgres; what you lose is the ability to run
`scripts.reingest_uploads`. Keep local copies of the workbooks — re-uploading is
idempotent by design.

**512 MB is tight for ingestion.** `MAX_UPLOAD_SIZE` allows 50 MB and ingestion
reads every sheet through pandas. A large workbook can exhaust the instance and
be killed mid-request. If that happens, lower `MAX_UPLOAD_SIZE` or upgrade the
instance rather than retrying.

## Redeploying

Both hosts deploy on push to the default branch. The backend re-runs
`scripts.migrate_schema` on every boot, so schema changes land automatically.
